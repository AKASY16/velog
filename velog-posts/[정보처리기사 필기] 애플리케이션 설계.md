<h4 id="이미-정의된-상위-클래스부모-클래스의-속성-및-연산을-하위-클래스자식-클래스-가-물려받는-것을-말한다">이미 정의된 상위 클래스(부모 클래스)의 속성 및 연산을 하위 클래스(자식 클래스) 가 물려받는 것을 말한다.</h4>
<h4 id="하위-클래스는-상위-클래스의-모든-속성과-연산을-다시-정의하지-않고도-즉시-사용할-수-있다-재사용성-향상">하위 클래스는 상위 클래스의 모든 속성과 연산을 다시 정의하지 않고도 즉시 사용할 수 있다. (재사용성 향상)</h4>
<h4 id="필요에-따라-새로운-속성을-추가하거나-상속받은-연산을-수정overriding하여-기능을-확장할-수-있다">필요에 따라 새로운 속성을 추가하거나, 상속받은 연산을 수정(Overriding)하여 기능을 확장할 수 있다.</h4>
<h4 id="단-하위-클래스는-상위-클래스-자체를-수정할-수는-없으며-상위-클래스는-하위-클래스의-추가된-내용에-대해-영향을-받지-않는다">단, 하위 클래스는 상위 클래스 자체를 수정할 수는 없으며, 상위 클래스는 하위 클래스의 추가된 내용에 대해 영향을 받지 않는다.</h4>

<h3 id="2-럼바우rumbaugh의-분석-기법">2. 럼바우(Rumbaugh)의 분석 기법</h3>
<h4 id="객체-모델링-동적-모델링-기능-모델링-3개로-이루어짐-객동기로-암기">객체 모델링, 동적 모델링, 기능 모델링 3개로 이루어짐. '객동기'로 암기.</h4>
<h4 id="객체object-모델링-시스템에서-요구되는-객체를-찾아-속성-연산-식별-객체간-관계를-규정해-객체-다이어그램으로-표시하는-것-정보-모델링이라고도-한다">객체(Object) 모델링: 시스템에서 요구되는 객체를 찾아, 속성, 연산 식별, 객체간 관계를 규정해 객체 다이어그램으로 표시하는 것. 정보 모델링이라고도 한다.</h4>
<h4 id="동적dynamic-모델링-상태도를-이용해-시간의-흐름에-따른-객체간의-제어-흐름-상호-작용-동작-순서-등의-동적-행위를-표현하는-모델링">동적(Dynamic) 모델링: 상태도를 이용해 시간의 흐름에 따른 객체간의 제어 흐름, 상호 작용, 동작 순서 등의 동적 행위를 표현하는 모델링.</h4>
<h4 id="기능functional-모델링-자료-흐름도를-이용해-프로세스들간의-자료-흐름을-중심으로-처리-과정을-표현한-모델링">기능(Functional) 모델링: 자료 흐름도를 이용해 프로세스들간의 자료 흐름을 중심으로 처리 과정을 표현한 모델링.</h4>
<br />

<h3 id="3-객체지향-설계-원칙solid-원칙">3. 객체지향 설계 원칙(SOLID 원칙)</h3>
<h4 id="단일-책임-원칙srp-single-responsibility-principle-객체는-1개의-책임만-가져야-하는-원칙-응집도는-높게-결합도는-낮게-설계되어야-한다는-원칙이다">단일 책임 원칙(SRP; Single Responsibility Principle): 객체는 1개의 책임만 가져야 하는 원칙. 응집도는 높게, 결합도는 낮게 설계되어야 한다는 원칙이다.</h4>
<h4 id="개방-폐쇄-원칙ocp-open-closed-principle-기존-코드의-변경-없이-기능이-추가될-수-있도록-코드가-설계되어야-한다는-원칙-상속과-다형성을-활용한다-공통-인터페이스를-한의-인터페이스로-묶어-캡슐화하는-것이-대표적-방법이다">개방-폐쇄 원칙(OCP; Open-Closed Principle): 기존 코드의 변경 없이 기능이 추가될 수 있도록 코드가 설계되어야 한다는 원칙. 상속과 다형성을 활용한다. 공통 인터페이스를 한의 인터페이스로 묶어 캡슐화하는 것이 대표적 방법이다.</h4>
<h4 id="리스코프-치환-원칙lsp-liskov-substitution-principle-자식-클래스는-부모-클래스에서-가능한-행위는-반드시-수행할-수-있어야-한다는-원칙-자식-클래스는-부모-클래스의-책임을-무시하거나-재정의하지-않고-확장만-수행해야함">리스코프 치환 원칙(LSP; Liskov Substitution Principle): 자식 클래스는 부모 클래스에서 가능한 행위는 반드시 수행할 수 있어야 한다는 원칙. 자식 클래스는 부모 클래스의 책임을 무시하거나 재정의하지 않고 확장만 수행해야함.</h4>
<h4 id="인터페이스-분리-원칙interface-segregation-principle-관계-없는-인터페이스와는-의존-관계를-맺거나-영향을-받지-않아야-하는-원칙-단일-책임-원칙이-객체가-갖는-하나의-책임이라면-인터페이스-분리-원칙은-인터페이스가-갖는-하나의-책임">인터페이스 분리 원칙(Interface Segregation Principle): 관계 없는 인터페이스와는 의존 관계를 맺거나, 영향을 받지 않아야 하는 원칙. 단일 책임 원칙이 객체가 갖는 하나의 책임이라면 인터페이스 분리 원칙은 인터페이스가 갖는 하나의 책임.</h4>
<h4 id="의존-역전-원칙dependency-inversion-principle-객체간-의존-관계가-성립할-때-본인보다-추상성이-높은-클래스와-의존-관계를-맺어야-한다는-원칙-일반적으로-인터페이스를-사용한다면-이-원칙은-준수됨">의존 역전 원칙(Dependency Inversion Principle): 객체간 의존 관계가 성립할 때, 본인보다 추상성이 높은 클래스와 의존 관계를 맺어야 한다는 원칙. 일반적으로 인터페이스를 사용한다면 이 원칙은 준수됨.</h4>

<h3 id="2-결합도의-종류">2. 결합도의 종류</h3>
<h4 id="자료data-결합도-모듈간-인터페이스가-자료-요소로만-구성될-때의-결합도">자료(Data) 결합도: 모듈간 인터페이스가 자료 요소로만 구성될 때의 결합도.</h4>
<h4 id="스탬프stamp-결합도-모듈간-인터페이스를-통해-배열-레코드-등-자료-구조가-전달될-때의-결합도">스탬프(Stamp) 결합도: 모듈간 인터페이스를 통해 배열, 레코드 등 자료 구조가 전달될 때의 결합도.</h4>
<h4 id="제어control-결합도-모듈이-모듈-내부의-논리적-흐름을-제어하기-위해-제어-신호로-통신하거나-제어-요소를-전달하는-결합도">제어(Control) 결합도: 모듈이 모듈 내부의 논리적 흐름을 제어하기 위해 제어 신호로 통신하거나, 제어 요소를 전달하는 결합도.</h4>
<h4 id="외부external-결합도-모듈에서-선언한-데이터변수를-외부의-다른-모듈에서-참조할-때의-결합도">외부(External) 결합도: 모듈에서 선언한 데이터(변수)를 외부의 다른 모듈에서 참조할 때의 결합도.</h4>
<h4 id="공통common-결합도-공유되는-공통-데이터-영역을-여러-모듈이-함께-사용할-때의-결합도">공통(Common) 결합도: 공유되는 공통 데이터 영역을 여러 모듈이 함께 사용할 때의 결합도.</h4>
<h4 id="내용content-결합도-모듈이-다른-모듈-내부의-기능-데이터-등을-직접-참조하거나-수정할-수-있을-때의-결합도">내용(Content) 결합도: 모듈이 다른 모듈 내부의 기능, 데이터 등을 직접 참조하거나 수정할 수 있을 때의 결합도.</h4>
<br />

<h3 id="4-응집도">4. 응집도</h3>
<h4 id="모듈-내부-요소가-서로-관련되어-있는-정도를-말함-모듈이-독립적인-기능으로-정의되어-있는-정도를-의미한다">모듈 내부 요소가 서로 관련되어 있는 정도를 말함. 모듈이 독립적인 기능으로 정의되어 있는 정도를 의미한다.</h4>
<br />

<h3 id="5-응집도의-종류">5. 응집도의 종류</h3>
<h4 id="우연적coincidental-응집도-모듈-내부의-각-구성-요소들이-서로-관련-없는-요소로만-구성된-경우의-응집도">우연적(Coincidental) 응집도: 모듈 내부의 각 구성 요소들이 서로 관련 없는 요소로만 구성된 경우의 응집도.</h4>
<h4 id="논리적logical-응집도-서로-유사하거나-특정-형태로-분류되는-처리-요소들로-1개의-모듈이-형성되는-경우의-응집도">논리적(Logical) 응집도: 서로 유사하거나, 특정 형태로 분류되는 처리 요소들로 1개의 모듈이 형성되는 경우의 응집도.</h4>
<h4 id="시간적temporal-응집도-특정-시간에-처리되는-몇-개의-기능을-모아-하나의-모듈로-작성할-경우의-응집도">시간적(Temporal) 응집도: 특정 시간에 처리되는 몇 개의 기능을 모아 하나의 모듈로 작성할 경우의 응집도.</h4>
<h4 id="절차적procedural-응집도-모듈이-다수의-관련-기능을-갖고있고-모듈의-구성-요소들이-그-기능을-순차적으로-수행할-때의-응집도">절차적(Procedural) 응집도: 모듈이 다수의 관련 기능을 갖고있고, 모듈의 구성 요소들이 그 기능을 순차적으로 수행할 때의 응집도.</h4>
<h4 id="교환적communication-응집도-동일한-입력-및-출력을-사용해-서로-다른-기능을-수행하는-구성-요소들이-모였을-경우의-응집도">교환적(Communication) 응집도: 동일한 입력 및 출력을 사용해 서로 다른 기능을 수행하는 구성 요소들이 모였을 경우의 응집도.</h4>
<h4 id="순차적sequential-응집도-모듈-내-하나의-활동에서-나온-출력-데이터를-다음-활동의-입력-데이터로-사용하는-경우의-응집도">순차적(Sequential) 응집도: 모듈 내 하나의 활동에서 나온 출력 데이터를 다음 활동의 입력 데이터로 사용하는 경우의 응집도.</h4>
<h4 id="기능적functional-응집도-모듈-내부의-모든-기능-요소들이-하나의-문제와-연관되어-수행될-경우의-응집도">기능적(Functional) 응집도: 모듈 내부의 모든 기능 요소들이 하나의 문제와 연관되어 수행될 경우의 응집도.</h4>
<br />

<h3 id="6-응집도의-정도약함---강함">6. 응집도의 정도(약함 -&gt; 강함)</h3>
<h4 id="우연적-응집도---논리적-응집도---시간적-응집도---절차적-응집도---교환적-응집도---순차적-응집도---기능적-응집도">우연적 응집도 -&gt; 논리적 응집도 -&gt; 시간적 응집도 -&gt; 절차적 응집도 -&gt; 교환적 응집도 -&gt; 순차적 응집도 -&gt; 기능적 응집도</h4>

<h3 id="1-명확성clarity">1. 명확성(Clarity)</h3>
<h4 id="기능이-중의적으로-해석되지-않도록-명확하게-작성되어야-한다는-원칙">기능이 중의적으로 해석되지 않도록, 명확하게 작성되어야 한다는 원칙.</h4>

<h3 id="2-재사용reuse">2. 재사용(Reuse)</h3>
<h4 id="이미-개발된-기능을-새-시스템-혹은-기능-개발에-사용할-수-있는-정도를-말함">이미 개발된 기능을 새 시스템 혹은 기능 개발에 사용할 수 있는 정도를 말함.</h4>

<h3 id="1-디자인-패턴design-pattern">1. 디자인 패턴(Design Pattern)</h3>
<h4 id="각-모듈의-세분화된-역할이나-모듈간-인터페이스와-같은-코드를-작성하는-수준의-세부적인-구현-방안을-설계할-때-참조할-수-있는-전형적인-해결-방식-또는-예제를-의미함">각 모듈의 세분화된 역할이나 모듈간 인터페이스와 같은 코드를 작성하는 수준의 세부적인 구현 방안을 설계할 때 참조할 수 있는 전형적인 해결 방식 또는 예제를 의미함.</h4>
<h4 id="패턴-유형으로는-생성-패턴-구조-패턴-행위-패턴이-있다">패턴 유형으로는 생성 패턴, 구조 패턴, 행위 패턴이 있다.</h4>
<br />

<h3 id="2-디자인-패턴-사용의-장·단점">2. 디자인 패턴 사용의 장·단점</h3>
<h4 id="범용-코딩-스타일로-구조-파악이-용이하고-생산성을-높이고-코드-재사용을-통해-시간-및-비용이-절약된다-또한-개발자-간의-원활한-의사소통이-가능하다">범용 코딩 스타일로 구조 파악이 용이하고 생산성을 높이고, 코드 재사용을 통해 시간 및 비용이 절약된다. 또한 개발자 간의 원활한 의사소통이 가능하다.</h4>
<h4 id="하지만-초기-투자-비용이-부담될-수-있다">하지만, 초기 투자 비용이 부담될 수 있다.</h4>
<br />

<h3 id="3-생성-패턴creational-pattern">3. 생성 패턴(Creational Pattern)</h3>
<h4 id="추상-팩토리abstract-factory-구체적인-클래스에-의존하지-않고-인터페이스를-통해-서로-연관-및-의존하는-객체들의-그룹으로-생성하여-추상적으로-표현함">추상 팩토리(Abstract Factory): 구체적인 클래스에 의존하지 않고, 인터페이스를 통해 서로 연관 및 의존하는 객체들의 그룹으로 생성하여 추상적으로 표현함.</h4>
<h4 id="빌더builder-잘게-쪼개진-인스턴스들을-조합해-객체를-생성">빌더(Builder): 잘게 쪼개진 인스턴스들을 조합해 객체를 생성.</h4>
<h4 id="팩토리-메소드factory-method-객체-생성을-서브-클래스에서-처리하도록-분리해-캡슐화한-패턴">팩토리 메소드(Factory Method): 객체 생성을 서브 클래스에서 처리하도록 분리해 캡슐화한 패턴.</h4>
<h4 id="프로토타입prototype-원본-객체를-복사해-객체를-생성하는-패턴">프로토타입(Prototype): 원본 객체를 복사해 객체를 생성하는 패턴.</h4>
<h4 id="싱글톤singleton-1개의-객체를-생성하면-그-객체는-어디서든-참조할-수-있지만-여러-프로세스가-동시에-참조할-수는-없음">싱글톤(Singleton): 1개의 객체를 생성하면 그 객체는 어디서든 참조할 수 있지만, 여러 프로세스가 동시에 참조할 수는 없음.</h4>
<br />

<h3 id="4-구조-패턴structural-pattern">4. 구조 패턴(Structural Pattern)</h3>
<h4 id="어댑터adapter-호환성-없는-클래스의-인터페이스를-사용할-수-있게-변환해주는-패턴">어댑터(Adapter): 호환성 없는 클래스의 인터페이스를 사용할 수 있게 변환해주는 패턴.</h4>
<h4 id="브릿지bridge-구현부에서-추상층을-분리해서-서로가-독립적으로-확장할-수-있도록-구성한-패턴">브릿지(Bridge): 구현부에서 추상층을 분리해서, 서로가 독립적으로 확장할 수 있도록 구성한 패턴.</h4>
<h4 id="컴포지트composite-여러-객체를-가진-복합-객체와-단일-객체를-구분없이-다루고자-할-때-사용하는-패턴">컴포지트(Composite): 여러 객체를 가진 복합 객체와 단일 객체를 구분없이 다루고자 할 때 사용하는 패턴.</h4>
<h4 id="데코레이트decorator-객체간-결합을-통해-기능을-확장할-수-있는-패턴-어떤-객체에-기능을-추가하기-위해-다른-객체를-갖다붙이는-방식">데코레이트(Decorator): 객체간 결합을 통해 기능을 확장할 수 있는 패턴. 어떤 객체에 기능을 추가하기 위해 다른 객체를 갖다붙이는 방식.</h4>
<h4 id="퍼싸트facade-서브-클래스보다-상위에-인터페이스를-구성함으로써-서브-클래스의-기능을-간편하게-사용할-수-있도록-하는-패턴">퍼싸트(Facade): 서브 클래스보다 상위에 인터페이스를 구성함으로써 서브 클래스의 기능을 간편하게 사용할 수 있도록 하는 패턴.</h4>
<h4 id="플라이웨이트flyweight-인스턴스를-매번-생성하는게-아니라-가능하면-공유해서-사용함으로써-메모리를-절약하는-패턴">플라이웨이트(Flyweight): 인스턴스를 매번 생성하는게 아니라 가능하면 공유해서 사용함으로써 메모리를 절약하는 패턴.</h4>
<h4 id="프록시proxy-접근이-어려운-객체와-접근하고자-하는-객처를-연결할-수-있게-인터페이스-역할을-수행하는-패턴">프록시(Proxy): 접근이 어려운 객체와 접근하고자 하는 객처를 연결할 수 있게 인터페이스 역할을 수행하는 패턴</h4>
<br />

<h3 id="5-행위-패턴behavioral-pattern">5. 행위 패턴(Behavioral Pattern)</h3>
<h4 id="책임-연쇄chain-of-responsibility-요청을-처리할-수-있는-객체가-둘-이상-있어서-만약-한-객체가-요청을-처리하지-못하면-다음-객체에게-넘어가는-형태의-패턴">책임 연쇄(Chain of Responsibility): 요청을 처리할 수 있는 객체가 둘 이상 있어서 만약 한 객체가 요청을 처리하지 못하면 다음 객체에게 넘어가는 형태의 패턴.</h4>
<h4 id="커맨드command-요청을-객체로-캡슐화하여-재이용하거나-취소할-수-있도록-요청에-필요한-정보를-저장하거나-로그에-남기는-패턴">커맨드(Command): 요청을 객체로 캡슐화하여 재이용하거나 취소할 수 있도록 요청에 필요한 정보를 저장하거나 로그에 남기는 패턴.</h4>
<h4 id="인터프리터interperter-언어에-문법-표현을-정의하는-패턴-sql-통신-프로토콜-등을-개발할-때-사용한다">인터프리터(Interperter): 언어에 문법 표현을 정의하는 패턴. SQL, 통신 프로토콜 등을 개발할 때 사용한다.</h4>
<h4 id="반복자iterator-접근이-잦은-객체에-대해서는-동일한-인터페이스를-사용하도록-하는-패턴">반복자(Iterator): 접근이 잦은 객체에 대해서는 동일한 인터페이스를 사용하도록 하는 패턴.</h4>
<h4 id="중재자mediator-객체간의-상호작용인터페이스을-캡슐화하여-객체로-정의한-패턴">중재자(Mediator): 객체간의 상호작용(인터페이스)을 캡슐화하여 객체로 정의한 패턴</h4>
<h4 id="메멘토mementor-특정-시점의-객체를-객체화시켜서-요청에-따라-객체를-특정-시점으로-되돌릴-수-있는-기능을-제공하는-패턴">메멘토(Mementor): 특정 시점의 객체를 객체화시켜서 요청에 따라 객체를 특정 시점으로 되돌릴 수 있는 기능을 제공하는 패턴.</h4>
<h4 id="옵서버observer-객체의-상태가-변화하면-상속된-다른-객체들에게-그것을-전달하는-패턴">옵서버(Observer): 객체의 상태가 변화하면, 상속된 다른 객체들에게 그것을 전달하는 패턴.</h4>
<h4 id="상태state-동일한-동작이지만-객체의-상태에-따라-다르게-처리해야할-때-사용하는-패턴">상태(State): 동일한 동작이지만, 객체의 상태에 따라 다르게 처리해야할 때 사용하는 패턴.</h4>
<h4 id="전략strategy-동일한-계열의-알고리즘을-개별적으로-캡슐화하여-상호-교환할-수-있게-정의하는-패턴-예를-들면-전략-패턴을-사용하지-않으면-게임에서-attack를-수행할-때마다-if문으로-칼을-들고-있는지-지팡이를-들었는지-활을-들었는지를-체크해-swordattack이-나갈지-magicattack이-나갈지-bowattack이-나갈지를-일일이-결정하는-코드를-작성해야-한다-전략-패턴을-사용한다면-currentweaponattack-만-사용해도-된다-무기를-갈아낄-때마다-currentweapon이-맞는-무기의-attack으로-연결해줄테니까">전략(Strategy): 동일한 계열의 알고리즘을 개별적으로 캡슐화하여 상호 교환할 수 있게 정의하는 패턴. 예를 들면, 전략 패턴을 사용하지 않으면 게임에서 attack()를 수행할 때마다 if문으로 칼을 들고 있는지, 지팡이를 들었는지, 활을 들었는지를 체크해 swordAttack()이 나갈지, magicAttack()이 나갈지, bowAttack()이 나갈지를 일일이 결정하는 코드를 작성해야 한다. 전략 패턴을 사용한다면 currentWeapon.attack() 만 사용해도 된다. 무기를 갈아낄 때마다 currentWeapon이 맞는 무기의 attack()으로 연결해줄테니까.</h4>
<h4 id="템플릿-메소드tempelete-method-상위-클래스에서-뼈대를-정의하고-하위-클래스에서-세부적인-처리를-구체화하는-구조의-패턴">템플릿 메소드(Tempelete Method): 상위 클래스에서 뼈대를 정의하고, 하위 클래스에서 세부적인 처리를 구체화하는 구조의 패턴.</h4>
<h4 id="방문자visitor-각-클래스들의-데이터-구조에서-처리-기능을-분리해-별도의-클래스로-구성하는-패턴">방문자(Visitor): 각 클래스들의 데이터 구조에서 처리 기능을 분리해 별도의 클래스로 구성하는 패턴.</h4>
